## 1. 固定 UP 通道（✅ 0.3.0 已修，诊断过程留档）

**现象**：日志里 `拉投稿失败 小约翰可汗：non-json: <!DOCTYPE html>` / `风控校验失败`。

**根因**：`lib/bili.mjs:201` 走 `/x/space/wbi/arc/search`，这个接口对**未登录**请求有两道校验：

1. WBI 签名（`w_rid`）—— 插件做了 ✅
2. 浏览器指纹 `dm_img_list` / `dm_img_str` / `dm_img_inter` + `web_location` —— 插件**没做** ❌

缺第 2 项直接被判成风险流量。

**实测（2026-10-28，同一 IP，UP=小约翰可汗 mid=23947287）**：

| 状态 | 请求 | 结果 |
|---|---|---|
| 游客 | 当前实现（只有 WBI） | `-352 风控校验失败`（连测 2 次稳定复现） |
| 游客 | 补 `dm_img_*` + `web_location` | ✅ 6 条投稿 |
| 登录 | 当前实现 | ✅ 连打 10 次全成功 |
| 游客 | 老接口 `/x/space/arc/search` | `-799 请求过于频繁` |
| 游客 | 动态流 `/polymer/web-dynamic/v1/feed/space` | `-412 request was banned` |

**为什么现在看起来正常**：2026-10-27 04:49 扫码登录后 `credential.json` 就位，请求带 SESSDATA，第二道校验自动过。
两个实例的 `feed.json` 都是 `upResolved: [{mid:"23947287", name:"小约翰可汗", count:6}]`。

**隐患**：`lib/pool.mjs:943` 失败就 `continue`，**没有兜底**。凭证一过期，固定 UP 就静默消失，UI 上只是少一栏。

**修法（两行活）**：
1. `userVideos` 补 `dm_img_list=[]&dm_img_str=...&dm_img_inter=...&web_location=1550101`（已实测登录/游客都可用）
2. 失败重试一次；仍失败就把原因写进 `feed.json`，前端「固定关注」空时显示「凭证失效，扫码登录后恢复」

**✅ 实际修完之后（0.3.0）**：第 1、2 条都做了，另外补了两件当初没想到的：
- `ensureBuvid()` 同时拿 `buvid4`（`finger/spi` 的 `b_4`）。只给 `buvid3` 时游客态仍然间歇 `-352`
- **全局节流 750ms**（`bili.mjs` 的 `spacePace()`）。实测 3 并发连打 10 个 UP 会有一半被 `-352` / HTML 拦截页打回；
  同样的请求串行打就基本不炸。节流做进 `userVideos` 而不是让调用方各自 `sleep`，省得以后再踩
- 拉失败时把 `{name, message}` 写进 `feed.upErrors`，「关注」页显示「拉不到 X 的投稿：…多半是 B站 登录过期了」

**诊断脚本**：`tools/up-probe.mjs`（四种写法对照）、`tools/rl-probe.mjs`（连打看会不会被封）。

## 2. 加载慢 + 重开 DSH 后空白（✅ 0.3.0 已修，账目留档）

**实测时长**（`~/.dsh/bili-jar/feed.json`）：`tookMs = 31707ms`、`curatorMs = 11379ms` ⇒ **一次重建 ≈ 43s**。

**为什么空白**：客户端 `feed` 只在内存（`client.js:514`），没有落 localStorage；服务端 `feed.json` 明明有昨天的卡片，但 `index.js:445`

```js
const fresh = feedCache && Date.now() - feedCache.ts < FEED_TTL   // FEED_TTL = 30 分钟
if (!force && fresh) return { ...feedCache, cached: true }
```

超过 30 分钟就**阻塞重建**再返回，客户端这 40 多秒什么都没有。

**31.7s 花在哪**（按代码数出来的）：

| 段 | 次数 × 耗时 | 小计 |
|---|---|---|
| 搜索（8 轴 × 2–3 词） | 21 ×（网络 0.4s + `sleep(400)`） | **~17s** |
| 决赛圈查详情（`pool.mjs:810`） | 12 × 串行（0.4s + `sleep(300)`） | **~8.4s** |
| 冷启动补详情（4 并发） | 2 批 | ~2.5s |
| 过期刷新（3 条） | 1 批 | ~1.5s |
| 固定 UP | 2 × 0.9s | ~1.8s |
| 粉丝区间（当前没开） | 10 × 0.8s 串行 | 0（若开会 +8s） |

**方案 A：让空白消失（优先做）**
1. **服务端 stale-while-revalidate**：`/feed`（不带 force）只要磁盘上有就**立刻返回** `{...feedCache, stale:true}`，后台起一次重建；重建完写盘。重建期间再次请求仍返回旧的那份。
2. **客户端 localStorage 快照**：面板一开先画上次的卡片（淡一点 + 一行「上次的，正在更新」），不等网络。
3. **挂载预热**：`apply()` 里若 feed 过期（> 2h）就延迟 5s 后台重建，用户点开时已经是新的。
4. 后台重建完成后**不自动替换**正在看的卡片，只在顶部弹「新的一批装好了 · 点此查看」——避免阅读中内容跳变。

**方案 B：缩短重建时间（43s → 20s 左右）**
1. 搜索改并发 3 + 抖动节流（替代固定 `sleep(400)`）：17s → **6s**。风控风险要真机验（刚实测过 `-412` 会被触发，所以并发别超过 3，失败重试一次）。
2. 决赛圈 12 条详情改 4 并发（复用 `backfillStats`）：8.4s → **2s**。
3. `enrichReasons` 的 5 条字幕/评论串行改并发 3：~5s → **2s**（这部分算在 `curatorMs` 里）。
4. 两段式返回：先给规则片单，策展完成后客户端再拉一次换成模型版 —— 11s 的策展就不阻塞首屏。

**注意**：`FEED_TTL` 现在是 30 分钟且**没有后台定时器**，等于「30 分钟内打开面板都是同一批，超过才重建一次」。
做完 SWR 后 TTL 的语义变成「多久算值得后台换一次」，可以放宽到 2 小时，省 B站请求 + LLM 费用。

### ✅ 实际做完之后（0.3.0）的实测

用 `out/harness.mjs`（把 `index.js` 装进假宿主、状态目录拷一份真实数据）跑：

| 项目 | 结果 |
|---|---|
| `GET /feed`（面板打开） | **74ms** 返回 5 张旧卡片，`stale:true, refreshing:true` |
| 后台探测 | `probe:run 8 次搜索 / 8415ms` → 触发完整重建 → 新片单落盘，`peek` 的 `ts` 变了 |
| 熟人名单 | `ups:list 熟人 0 / 观察 11 / 拉黑 0`（1 次互动=观察，3 次才转正，符合定义） |
| 熟人投稿 | `stats.upList = {people:6, items:60}` |
| 回音室 | `stats.echoGuard = {cap:2, picked:0, trimmed:0}`；单测 6 条守着 |
| 全套单测 | 118 / 118 通过 |

`FEED_TTL` 已从 30 分钟改成 3 小时，且只用来决定「角标要不要说后台在更新」——
真正的重建时机交给 `lib/refresh.mjs`（3h 打开 / 6h 自动 / 24h 全量）。
